## 1. 密钥部署审查

读取点只有 `readAssistantSealKey()`（`src/lib/assistant-turn-seal.ts`）。`POST /api/scene-assistant` 在解析请求之前调用它。变量名是 `ASSISTANT_TURN_SEAL_KEY`。

校验规则：

- 缺失、不是字符串，或去掉首尾空白后为空：抛出配置错误。路由把它变成 HTTP 500，正文是 `Generation service configuration error.`。前端会显示现有的「生成服务配置有误」。
- 非空值按原样使用，**不会**再 trim。平台若在值末尾写入换行，这个换行就是密钥的一部分。各实例必须逐字节相同。
- 签名是 HMAC-SHA256。规范字符串以代码常量 `rg2-seal-v1` 开头，然后是角色、`questionId`、消息种类、授权模式、进度、作品、场景和正文哈希。没有密钥编号。

这个名字不以 `NEXT_PUBLIC_` 开头，因此 Next 不会把它内联进浏览器包。签名只在路由里计算。客户端组件为了做历史过滤，会引用同一模块里的纯函数；那不会把密钥值带进浏览器。不要把这个变量改名为 `NEXT_PUBLIC_` 开头。

| 环境 | 放置位置 | 要求 |
|---|---|---|
| 本地 | `.env.local`，与 `GEMINI_API_KEY` 同级。仓库没有 env 模板，README 的示例块也还没有这一项 | 只在本机。不要提交。改完后重启 `npm run dev` |
| Vercel Preview | 项目 Environment Variables，勾选 Preview | 该预览环境内所有函数实例读到同一值 |
| Vercel Production | 同一项目，勾选 Production。现场是 `https://raree-show-web.vercel.app` | 生产实例使用同一值。不要和生产预览共用一把密钥 |

预览和生产应使用不同密钥。对话只存在浏览器内存里，密钥不一致不会迁移历史，但可以避免把预览环境签过的请求拿到生产环境去验证。

轮换：

- 当前实现只认一把当前密钥。更换后，已经显示在屏幕上的助手消息签名会立刻验证失败。
- 下一次无剧透或会话剧透请求会丢掉这些助手消息，不再送进模型。屏幕上的文字还在。
- 没有旧密钥并行校验，也没有密钥编号。轮换期间不能「先签新的、仍认旧的」。
- 打开中的对话会失去已签名的模型历史。用户可以继续看旧气泡，但模型不再记得它们。这是可接受的，因为本来也没有会话数据库。
- 轮换步骤：在对应环境写入新值，重新部署，让所有实例同时切换。不要只改其中一台。

操作时不要把密钥写进工单、聊天或日志。生成一把高熵随机值即可，例如 32 字节再编码。本地文件保持不入库。

未配置时的验收：打开助手提问，应看到配置错误，而不是「尚未揭晓」或授权卡。

## 2. 浏览器验收清单

位置：作品《三国演义》，第一条路线。第 0 帧用于张角的问题，第 2 帧用于刘关张。界面语言用中文。开发者工具打开 Network，过滤 `scene-assistant`。本地必须已经配置上一节的密钥。

下列预期来自当前 `ReadingRouteAssistant` 和路由，不是新设计。

### 2.1 初次打开

操作：点「询问故事向导」。

预期 UI：没有「剧透模式已开启」。消息为空。

请求：还没有。

历史：空。

### 2.2 无剧透提问

操作：在第 0 帧发送「张角是怎么发家的？」。

预期 UI：一条用户气泡，一条助手气泡。没有授权卡，没有「含剧透」。

请求：`spoilerMode` 为 `"none"`。没有 `authorizedQuestionId`。最后一条用户消息带新的 `questionId`。

历史：成功后的助手消息带 `assistant-turn-seal`。`spoilerDisclosure` 为 false。

### 2.3 授权卡的三个按钮

操作：在第 0 帧发送「张角最后的下场是什么？」。若模型发出标记，气泡下出现授权卡。

暂不剧透：

- UI：按钮消失，不再出现第二条用户气泡，也不再出现新的助手气泡。
- 请求：没有第二次 `POST`。
- 历史：原问题和带标记的那次回答都留在屏幕上。会话仍是无剧透。

仅本次回答允许剧透：

- UI：三个按钮立即不可用。不新增用户气泡。新的助手回答出现在卡片下面，并带「含剧透」。标题下不出现「剧透模式已开启」。
- 请求：`spoilerMode` 为 `"single_request"`。`authorizedQuestionId` 等于屏幕上那条原始用户消息的 `questionId`。`messages` 里该用户消息只出现一次。
- 历史：这次回答的 seal 中 `spoilerDisclosure` 为 true，`spoilerMode` 为 `"single_request"`。

开启本次对话剧透模式：

- UI：按钮不可用。标题下出现「剧透模式已开启」，旁边有「关闭剧透」。新回答带「含剧透」。
- 请求：`spoilerMode` 为 `"conversation"`。不要带 `authorizedQuestionId`。`questionId` 仍是原问题。
- 历史：seal 的 `spoilerMode` 为 `"conversation"`。

### 2.4 单次授权之后的新问题

操作：在 2.3 的单次授权成功后，另发一个新问题。

预期 UI：没有持久的剧透条。

请求：`spoilerMode` 为 `"none"`。新的 `questionId`。上一条剧透助手消息不在这次请求的 `messages` 里。

历史：屏幕上仍能看到刚才的剧透回答。

### 2.5 会话模式连续请求

操作：开启会话剧透后，再发一个不同问题。

预期 UI：剧透条还在。不再出现授权卡。新回答带「含剧透」。

请求：`spoilerMode` 为 `"conversation"`。历史里可以包含上一条签名有效的剧透回答。

### 2.6 关闭剧透后的下一条

操作：点「关闭剧透」，再发新问题。不要关面板。

预期 UI：剧透条消失。已经生成的剧透气泡还在。

请求：`spoilerMode` 为 `"none"`。剧透助手消息不在 `messages` 里。普通的无剧透回答若签名有效，可以留下。

正在流出的那一条：点「关闭剧透」不会中止它。它按已经发出的 `conversation` 请求结束。下一条才是 `"none"`。

### 2.7 关闭面板再打开

操作：在有对话、且会话剧透已开启时，点面板的关闭，再点「询问故事向导」。

预期 UI：同一批消息还在。剧透条还在。

请求：开关面板本身不发请求。

例外：关闭时如果正在生成，当前实现会中止这次生成。这和只点「关闭剧透」不同。

### 2.8 新对话

操作：点「新对话」。

预期 UI：消息清空，输入清空，剧透条消失。

请求：进行中的生成被中止。没有新的成功 seal。

历史：内存中的 `questionId` 和 seal 都不再存在。

### 2.9 生成期间重复点击

操作：授权卡出现后，快速连点「仅本次」或在回答流出时再点发送。

预期 UI：按钮在 `streaming` 时禁用。第一次点击进入 `send()` 后，`sendingRef` 会挡住第二次。

请求：只有一个 `single_request` 或 `conversation` 请求。

### 2.10 生成期间改状态

操作：会话剧透的回答正在流出时点「关闭剧透」。

预期：当前请求不改回无剧透。它已经带了 `conversation`。完成后仍可能带「含剧透」。下一条是 `"none"`。

操作：流出时点面板关闭。

预期：这次生成被中止，没有成功 seal。再打开后面板仍保留已取消前的文字和剧透会话状态。

### 2.11 本轮没有做的检查

没有在浏览器里执行以上点击。Network 里的字段名以本节为准，以实际请求为准做核对。

## 3. 提前泄漏根因

观察：第 0 帧、无剧透，问题是「张角最后的下场是什么？」。一次生成的可见散文包含「因病去世」，同时流末尾有 `<<RAREE_SPOILER_REQUEST>>`。标记被剥掉后，死亡情节留在气泡里，授权卡仍会出现。

### 3.1 各层实际做了什么

Prompt（`assistant-system-prompt.ts`）在无剧透的 Case C 里要求：先写已读材料支持的部分，不要写出死亡或战败，最后另起一行写标记。Case B 又允许用模型知识解释已经露面的事件。第 0 帧的 caption 已经写了张角领导黄巾起义。模型因此同时收到「可以补充这段起义」和「不要写他的下场」。

`assistant-request-prompt.ts` 只选择语言并调用上面的组装函数。它不判断剧透，也不截断模型输出。

检索在这次请求里仍是无剧透：只有当前进度内的 caption。后文 caption 没有进入提示词。泄漏的句子不是数据库里的未读 caption，而是模型自己写的。

`assistant-visible-stream.ts` 用 `SpoilerMarkerTail` 处理 `text-delta`。它只暂扣末尾约一个标记的长度（标记 25 个字符再加 1）。更早的增量立刻重新编码成 `text-delta` 发给浏览器。流正常结束时才调用 `splitSpoilerMarker`。标记必须是全文的结尾才会被认作授权请求；标记前面的全部文字被当作安全散文，随后写入 seal 的正文哈希。

`route.ts` 在无剧透且标记成立时，把这条消息标成 `authorization_request`。它不检查散文里有没有结局。Gemini 是主模型；OpenRouter 只在第一个正文分块之前接替。一旦「因病去世」作为第一个正文发出，语义锁已经落下，另一家供应商不能收回这段文字。

### 3.2 为什么会先写出结局

模型把「他后来死了」当成对问题的直接回答，并把授权标记放在事实后面，当作补充手续。Prompt 禁止这件事，但禁止发生在采样之后。相邻的 Case B 又鼓励它用自身知识把已经出现的黄巾起义讲完。死亡既是历史常识，也是未读情节。提示词没有一个先于采样的硬开关。

所以这不是 SQL 可见性被绕过。无剧透检索没有把后文 caption 交给模型。

### 3.3 这是哪一类问题

三者都有份，但决定用户是否看见结局的是交付边界。

- Prompt 问题：它只能降低模型写出结局的概率。同一条规则下，有的运行只输出标记，有的运行先写死亡再写标记。
- 生成顺序问题：产品要求先写散文、最后写标记。模型若把结局写进散文，顺序本身就是泄漏顺序。
- 架构问题：服务端把「标记之前的文字」定义成可以立刻展示的安全散文。标记只决定要不要加卡片，不决定前面的句子能不能离开服务器。

### 3.4 现有 SSE 机制为什么挡不住

暂扣窗口大约 26 个字符，只为了不把被切碎的标记画出来。一个完整句子远长于这个窗口，会在标记出现之前若干个分块就已经到达浏览器。结束时的剥离只删除标记，不删除标记前的句子。授权卡是在泄漏已经显示之后追加的。

### 3.5 有没有不依赖模型自觉的办法

有。前提是：授权决定完成之前，用户可见的文字不能来自模型的自由叙述。

做不到的办法：继续让模型边写边流出，同时指望它最后才写标记。

## 4. 方案对比

| 方案 | 安全边界 | 复杂度 | 延迟 | Token | 误判 | 供应商 | 安全散文加卡片 |
|---|---|---|---|---|---|---|---|
| A. 只改 Prompt | 不改变。模型仍可先写结局 | 低 | 不变 | 略增提示词 | 仍会漏，也会过度要授权 | 兼容 | 保留，但散文仍可能含结局 |
| B. 两阶段：先判定，再生成叙述 | 改变生成边界。判定完成前不生成下场 | 中 | 多一次短调用，然后才开始流式 | 判定很短；不需要授权时再生成全文 | 会把背景问题误判成需要授权，或漏判 | Gemini 与 OpenRouter 都能做一次短 `generateText`。判定发生在叙述流的语义锁之前，失败仍可换供应商 | 可以。卡片用判定结果；安全散文不要用叙述模型的自由文本 |
| C1. 缓冲到流结束，标记出现就整段丢弃模型文字，只显示卡片 | 改变交付边界。这次泄漏不会到达浏览器。模型仍然生成了结局 | 低 | 第一个字要等到全文结束 | 结局的 Token 已经花掉 | 标记漏写则整段照常展示，泄漏仍在 | 不改变供应商切换。缓冲发生在获胜流上 | 模型写的安全散文会一起被丢掉 |
| C2. 缓冲并用分类器删除疑似剧透句 | 不改变边界。分类器会漏、会误删 | 高 | 全文结束或逐句延迟 | 额外分类调用 | 高 | 再引入一次模型调用 | 表面上可以，句子边界不稳定 |
| D. 判定只用封闭枚举；授权前的可见文字只来自已揭示 caption 或固定卡片 | 改变生成和交付。授权前没有模型叙述可以泄漏结局 | 中高 | 与 B 相同，多一次短调用 | 判定短；授权后才生成长回答 | 枚举仍会误判要不要授权，但不能把结局写进授权前的气泡 | 与 B 相同 | 保留。安全散文由服务端从已截断 caption 抽出，卡片文案仍用 locale |

A 和 C2 只降低风险。B 改变「何时开始生成叙述」。C1 改变「模型已经生成的文字是否交给浏览器」，但不阻止生成。D 同时改变生成和交付：授权前的气泡里没有模型自由叙述。

## 5. 推荐

采用 D，作为 P2 的泄漏修复。不在本轮改代码。

理由：当前事故的句子来自模型，不来自未读 caption。只要授权前展示模型散文，标记就只能当卡片开关，不能当闸门。D 让第一次调用只返回需要授权或不需要。需要授权时，浏览器看到的是固定卡片，加上服务端从当前已揭示 caption 摘出的句子。完整叙述只在 `single_request` 或 `conversation` 通过校验之后才开始流式生成。

A 可以继续当作文案收紧，不能当作修复。C1 可以作为 D 之前的短补丁：它能挡住这一次「先写死亡再写标记」，代价是失去流式，并且模型写的安全解释也会被丢掉。若 P2 直接做 D，就不必先做 C1。

## 6. P2 建议拆分

1. 部署：按第 1 节写入三个环境的密钥，并用配置错误路径做一次无密钥检查。不把密钥写进仓库。
2. 浏览器：按第 2 节点完。未点之前不要把交互标成已通过。
3. 泄漏修复：实现第 5 节的 D。授权前不流式生成叙述。
4. 回归：第 0 帧「张角最后的下场」在无剧透时，气泡中不出现死亡、开棺或战败。授权之后的回答仍可以写这些，并带「含剧透」。第 0 帧「怎么发家」仍直接回答，不弹卡片。
5. 不做：阅读账本、账户级剧透偏好、会话数据库、自动话题识别、把 Story Oracle 扩到 summary。

## 7. 仍然存在的理论限制

- 授权之后的叙述仍来自模型。它可以写错，也可以把小说和史书写混。HMAC 只证明这是哪一次检索模式签出的正文。
- 判定枚举仍可能把背景问题要成授权，或把该授权的问题放行。放行之后的全文生成仍可能说出未读情节。D 堵住的是授权决定之前的那一段。
- 用户可以在下一问里自己打出剧情。服务端不能把这句鉴定成上一轮的助手泄漏。
- 无剧透路径仍然信任客户端申报的进度。没有阅读账本就无法证明进度没有被抬高。
- 已入库路线不是整部原著。授权范围也不是整部原著。
- 模型权重里的情节无法删除。物理边界只作用于注入的 caption 和授权前是否展示模型叙述。
