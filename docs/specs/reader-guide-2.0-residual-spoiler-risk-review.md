## 1. 固定失败证据

进度都是《三国演义》第一条路线、第 0 帧。caption 只揭示黄巾起义爆发和官军失利后的招募。下列回答来自 P2-B.1 之后的真实模型，保留原文含义，不因关键词消失就判为通过。

| 问题 | 次数 | 观察到的越界 | 类型 |
|---|---|---|---|
| 介绍一下张角 | 2 | 没有再写南华老仙授书，也没有再写群雄并起。回答停在已揭示起义和招募 | 本轮未复现前史泄漏 |
| 太平道是什么 | 2 | 把组织写成「撼动汉室统治根基」「震撼了汉朝的统治」 | 事后视角评价；未揭示后续因果 |
| 张角为什么发动起义 | 1 | 补出 caption 未出现的张宝、张梁 | 未揭示人物关系 |
| 张角起兵是为了什么 | 1 | 停在腐败、灾荒和可见起义 | 本轮未越界 |
| 南华老仙授书 | 早前「介绍一下张角」 | 入山遇仙、获授《太平要术》 | 未揭示前史。P2-B.1 后的两次介绍没有复现 |
| 「群雄并起」 | 早前介绍、太平道、起义原因 | 把起义写成开启后来的群雄时代 | 事后视角评价；未揭示后续因果。无剧透回答里这一表述本轮没有复现；授权回答里出现是允许的 |

死亡、胜负、后世影响和后来的身份，在这轮被 Stage 1 判成需要授权，没有进入 Stage 2。那只说明问题级闸门拦住了这些问法，不说明 Stage 2 在放行后能守住事实。

## 2. 现有架构为什么守不住答案

当前顺序是：

1. Stage 1 看问题和已揭示 caption，给出一个问题级判定。
2. `answer_allowed` 之后，Stage 2 按普通生成写出整段回答。
3. Stage 2 仍能使用模型参数里的原著知识。
4. 没有任何独立步骤检查回答里的每一项故事事实是否已被揭示。

Stage 1 的输出是「这个问题可以回答」，不是「这句事实可以披露」。宽泛问题正好落在这个缝里：

- 「介绍一下张角」可以只讲已揭示的领袖身份，也可以滑成完整传记。
- 「太平道是什么」可以讲它是起义所依托的宗教组织，也可以滑成组织后来如何撼动汉室。
- 「张角为什么发动起义」可以讲 caption 里的腐败、灾荒和已经爆发的起义，也可以补上未出场的兄弟。

这些问题不应一律变成授权卡，因为安全的部分值得回答。放行也不等于允许补全人物、组织和后来的因果。问题级判定没有一份「允许披露的事实清单」可以传给 Stage 2，Stage 2 的采样也不会逐句回来接受检查。Prompt 只能降低概率。P2-B.1 已经写明进度边界，模型仍然写出了事后评价和未揭示的人物关系。

模型权重里的完整剧情删不掉。没有阅读账本时，`none` 仍信任客户端进度。这些都不是本评估要新做的功能。

## 3. 方案比较

### 方案 A：继续强化 Prompt

开发成本低，主要是改提示和回归。延迟和 token 增加很少。对换一种说法的鲁棒性差：同一类事后评价可以不用「群雄并起」这四个字，改说「撼动统治根基」。当前失败已经说明，把禁令写得更细不能当作下一层安全边界。它适合继续压低明显泄漏的频率，风险水平仍是「有时会漏」。

### 方案 B：草稿生成后再做独立审查

Stage 2 先写出完整草稿，不立刻流式给用户。审查器只看已揭示 caption、当前问题和草稿，标出未经授权的故事事实，然后拒绝、删改或放行。

它有机会抓住未揭示前史和未出场人物，因为审查发生在答案文本上，而不是只看问题。隐性剧透仍会漏：审查器如果也是模型，它同样可能把「撼动汉室」当成背景，或漏掉一句没有专名的事后评价。这是第二次概率判断，不是结构保证。

成本是多一次模型调用，延迟从首字流式变成整段缓冲后再交付。要获得这个检查，现有「边生成边把 text-delta 发给浏览器」必须改成缓冲后交付。授权卡路径可以不变，因为它本来就不跑 Stage 2。

### 方案 C：要求每条事实自报来源

可以要求草稿把故事事实分成「caption 原文」「静态背景」「模型记忆」。逐条检查在工程上可行，但来源标签不是证据。模型可以把张宝、张梁标成静态背景，标签本身无法证明 caption 里有他们。确定性验证只能核对「自称来自 caption」的句子是否真是 caption 子串。自称是静态背景的句子仍然没有外部证据。因此 C 不能单独作为闸门。它最多给 B 提供一个可测试的中间表示。

### 方案 D：静态背景白名单

允许不依赖未揭示故事事件的一般知识：时代、地理、制度、习俗、宗教和社会的一般描述。人物传记、人物关系、组织后来的历史、故事专属事件，必须能在已揭示 caption 里找到依据。

这会收窄阅读辅助。宽问题的回答会更短，有些合理的文化背景也会变少。若白名单要做成可查询的数据，就需要新的背景知识结构，并决定它进不进 Story Oracle。当前 Oracle 只哈希注入的 caption。把白名单放进 Oracle 会扩大 Oracle 的对象，和现在的 caption-only 边界不相容。若白名单只是写在审查规则里、不进数据库，则不必改 Oracle，也还没有新表。

用一部分回答丰富度换更窄的披露边界，是值得的，但只作为审查规则，不作为新的检索对象。

## 4. 推荐

本节是当时的分析结论，不是当前待办。2026-11-17 已暂停实施，见两阶段设计第 17 节。

推荐下一步先修订冻结设计，再实现 **缓冲后的答案审查（方案 B），审查规则采用方案 D 的边界，并用方案 C 只核对称作 caption 原文的子串**。

不推荐把方案 A 当作下一层边界。它已经有真实失败。不推荐单独采用方案 C。模型给自己贴的来源标签不能当成证据。不推荐为方案 D 新建背景知识表或扩大 Story Oracle。那会改变检索边界，而当前问题出在生成之后。

需要改变的架构边界：

- `answer_allowed` 不再表示可以把 Stage 2 的 token 直接发给浏览器。
- 无剧透 Stage 2 改为先缓冲草稿，审查通过后再一次性或分段交付。
- 审查不通过时，用户看到的是已揭示部分或当前进度无法确认，而不是草稿原文。
- 授权后的 Stage 2 保持现在的流式交付，不套这层审查。
- HMAC 仍只签最终交给用户的正文。审查器的中间草稿不签名、不进历史。

延迟和成本：无剧透且被放行的问题多一次审查调用，首字变晚。授权问题和授权卡路径不加这层。回答会更短，宽问题不再展开完整传记和组织后来的历史。

可测试的验收标准，仍不是零泄漏证明：

- 草稿里的未揭示前史、未出场人物关系、组织后来的历史和事后评价，不会出现在用户可见正文里。
- caption 子串检查失败的句子不能以「来自 caption」放行。
- 「介绍一下张角」「太平道是什么」「张角为什么发动起义」仍要回答已揭示部分，而不是整题变成授权卡。
- 授权后的回答仍可以写后续剧情，并保持流式。
- 审查器漏判时，记录为残余风险，不写成结构保证。

这需要修订冻结设计里「`answer_allowed` 后直接流式 Stage 2」的交付方式。在设计修订之前，不开始实现。
